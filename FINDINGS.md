## Comparative Benchmarks (vs mvzr, RE2, Rust `regex`, .NET `Regex` & Python `re`)

A reproducible cross-engine harness lives in this repo (`run_all.sh`). It
builds six
harnesses — zig-regex, **[mvzr](https://github.com/mnemnion/mvzr)** (a small
zero-allocation Zig backtracking VM), **RE2** (Google), the
**Rust `regex` crate**, **.NET `System.Text.RegularExpressions`** (its default
backtracking engine), and **Python `re`** (stdlib backtracking engine) — and
runs the *same*
operation (count all leftmost, non-overlapping matches)
over **byte-identical** input from a deterministic 1 MiB corpus. Compile time
and search time are timed in separate loops; reported numbers are the median of
each timed loop. A correctness gate asserts all engines agree on match counts
before any timing is reported.

Run it with:

```bash
./run_all.sh
# → results.md  (full tables)
# → results.csv (raw data)
```

Measured on Apple Silicon (macOS, aarch64), Zig 0.16.0 / rustc 1.85 / RE2
(Homebrew) / .NET 10 / CPython 3.9, all engines built optimized
(zig-regex `-OReleaseFast`). See `results.md` (regenerated by `run_all.sh`) for
the complete per-workload, per-size tables.

### Optimizations applied

Two **semantics-preserving** changes (the locked Pike-VM regression suite and
the cross-engine correctness gate both still pass — match counts are
byte-identical to before):

1. **256-bit character-class bitmap.** `CharClass.matches` was an O(ranges)
   linear scan run for every input byte on every live thread. Each `char_class`
   NFA transition now carries a precomputed 256-bit membership table (negation
   folded in), so the per-byte test is a single O(1) bit lookup.
2. **First-byte prefilter (`first_byte_set`).** The optimizer computes the
   set of bytes any match may legally *start* with — a strictly necessary
   condition that generalizes the existing literal-prefix filter to
   quantifiers, character classes, and **alternation-of-literals**
   (`cat|dog|bird|fish` → `{c,d,b,f}`). The scan skips positions whose byte
   cannot begin a match instead of re-running the NFA there. Disabled when the
   pattern can match empty or no selective set exists; case-folded under `-i`.
3. **SIMD `@Vector` prefilter scan (`src/prefilter.zig`).** The candidate-byte
   scan was a scalar one-byte-at-a-time loop. It now classifies the validated
   256-bit `first_byte_set` bitmap into the cheapest portable `@Vector` kernel —
   `single` (`std.mem.indexOfScalarPos`), `multi` (≤8 byte equalities, OR-ed in
   the u8 domain), `ranges` (≤8 unsigned `(c -% lo) <= span` tests), or scalar
   `bitset` fallback — scanning `std.simd.suggestVectorLength` bytes per step
   with a `@reduce`-guarded `std.simd.firstTrue`. The SIMD predicate is derived
   *losslessly* from the same bitmap, so it is byte-identical to the scalar test
   (leftmost-first preserved; differential + regression suites green). Portable
   with no per-target branches or asm: NEON on aarch64, SSE2/AVX2 on x86_64
   (cross-codegen verified for both; runtime-validated on aarch64).

   Isolated SIMD-vs-scalar microbenchmark (16 MiB, single late match, this
   toolchain): single byte **11×**, single range (`[0-9]+`) **6×**,
   multi/4-range **~2.5×**.

Cumulative `feat/leftmost-first-linear-findall` vs `main`, 32 KiB,
match counts byte-identical (linear single-pass `findAll` + first-byte
prefilter + SIMD scan combined):

| Workload | main (search / MB/s) | current (search / MB/s) | Speedup |
|----------|----------------------|-------------------------|---------|
| `literal` (`Sherlock`)         | 11.85 ms / 2.77 | 0.67 ms / 48.96 | **~17.7×** |
| `alternation` (`cat\|dog\|bird\|fish`) | 42.99 ms / 0.76 | 3.35 ms / 9.78 | **~12.9×** |
| `quantifier` (`a+`)            | 17.05 ms / 1.92 | 2.57 ms / 12.76 | **~6.6×** |
| `digits` (`[0-9]+`)            | 17.46 ms / 1.88 | 3.08 ms / 10.64 | **~5.7×** |
| `ipv4`                         | 21.13 ms / 1.55 | 6.26 ms / 5.23  | **~3.4×** |
| `word` (`\w+`)                 | 18.87 ms / 1.74 | 14.30 ms / 2.29 | ~1.32× |

`\w+` gains least: its first-byte set covers ~63 of 256 bytes and the English
corpus is mostly word characters, so almost no positions are skippable and the
`ranges` kernel does its heaviest 4-range work on nearly every chunk. The
former genuine quadratic (re-running the NFA from every start inside a long
run) is gone — `findAll` is a single linear pass — so what remains for `\w+`
is the irreducible per-byte NFA simulation cost.

### Interpretation

- **.NET and zig-regex win on compile latency.** .NET compiles in ~0.3–1.5 µs
  and zig-regex in ~1.5–31 µs (heaviest: `ipv4` ~29 µs) — both competitive with
  RE2 (1–5 µs) and far faster than Rust, which pays a large up-front
  automaton-construction cost (e.g. ~127 µs for `\w+`, ~474 µs for the e-mail
  pattern). zig-regex trades a higher fixed setup cost for fast compilation of
  realistic patterns.
- **.NET's default engine is fast but backtracking.** On realistic patterns it
  sustains ~60–1600 MB/s (between RE2 and Rust, occasionally beating RE2 on the
  e-mail pattern), with very low compile latency. But it is a backtracking
  engine: on `(a+)+b` over 50 000 `a`s it exhibits **catastrophic
  backtracking** and only escapes via the 2 s `MatchTimeout` the harness sets —
  exactly the failure mode the linear-time engines (and zig-regex's compile-time
  ReDoS guard) exist to prevent.
- **Python `re` is the slowest production engine but still clearly beats
  zig-regex's `findAll`.** It runs at ~37–2685 MB/s (3–30× slower than
  RE2/.NET on heavier patterns) yet is still ~10–50× faster than zig-regex on
  the heavier 32 KiB workloads (and far more on tiny inputs, where zig-regex's
  ~µs compile + setup overhead dominates) because it scans linearly with a
  tuned C engine. It is also a
  backtracking engine and **catastrophically backtracks on `(a+)+b`**; since a
  C-level match never returns to the interpreter loop, Python signal handlers
  cannot interrupt it, so the harness runs that one workload in a child process
  with a hard 2 s wall-clock timeout (→ `TIMEOUT`).
- **`findAll` is now linear (single-pass leftmost-first NFA).** `Regex.findAll`
  (and the lazy iterator) no longer restart the VM per candidate start: one
  Pike-VM simulation scans the whole input, seeding a start thread at each
  position at lowest priority and relying on depth-first transition-order
  closure + sparse-set first-writer-wins dedup to keep leftmost-first priority,
  yielding every non-overlapping match in O(n·m). The first-byte / literal
  prefilters are retained purely to skip dead regions faster; correctness no
  longer depends on them, so the previously quadratic `\w+`-over-word-dense
  case is now linear too (regression-locked). The engine switched from
  leftmost-longest (POSIX) to **leftmost-first** (Perl/RE2/Rust) so the NFA and
  backtracking engines now agree; lazy quantifiers (`*?`, `+?`, `??`, `{m,n}?`
  without backrefs/lookaround) run on the fast NFA instead of the backtracker.
  Harness input is no longer capped at 32 KiB (now up to 1 MiB).
- **The ReDoS guard is a real usability trade-off.** `pattern_analyzer`
  rejects `(a+)+b` *and* the realistic e-mail pattern
  `[\w.+-]+@[\w-]+\.[\w.-]+` at compile time (`PatternTooComplex`). RE2 and
  Rust accept both and run them in linear time. The guard prevents catastrophic
  backtracking but also blocks legitimate patterns the linear-time engines
  handle safely.
- **Correctness holds.** Wherever zig-regex runs, its match counts match RE2,
  Rust, .NET, and Python exactly across every workload and input size (enforced
  by the harness's correctness gate).

> Note: zig-regex's linear-time property comes from a single NFA (Pike-VM)
> simulation. There is now a SIMD `@Vector` *prefilter* fast path (start-byte
> scan), but no lazy-DFA / SIMD *matching* fast path like RE2 or Rust `regex`.
> The remaining end-to-end gap versus RE2/ripgrep is dominated by the per-byte
> NFA-simulation cost (every live thread stepped per input byte) and this Zig
> 0.16 toolchain's weak codegen — the untouched `std.mem.indexOf` literal path
> measured only ~0.18 GB/s. The prefilter accelerates *finding* the next match
> start; it cannot speed up the simulation once the automaton is awake, which is
> why match-dense workloads (`\w+`) gain least.
